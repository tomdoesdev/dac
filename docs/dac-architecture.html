Architecture

How DAC is put together, and why each part is shaped the way it is: the ports-and-adapters split, the resolve ladder, the credential helper protocol, the tamper-evident object cache, and the decisions those follow from.

Structure

Shape of the system

DAC is ports and adapters with the ports in the middle. internal/application holds every command and defines the three interfaces it needs — an object store, a fetcher, and a progress reporter. It imports none of their implementations. internal/cache and internal/httpclient import it, and internal/cli is the only place that knows how to build one from the other.

Flag definitions, argument parsing, service construction, human summary strings, exit status. It owns every default and every environment variable, so nothing below it reads the environment.

▼

Every command lives here as a method on one Service: Add, Pull, Verify, Path, Remove, Init, Info, Export, Import, CacheGC, VerifyCache. Nothing here knows what HTTP is.

▼

▼

Small, individually testable, and deliberately placed below the layer that would otherwise own them — urlpolicy sits under both the manifest and the HTTP client because both apply it.

Why the dependency points this way

The interfaces are narrow enough to fake, which is what makes the command tests real tests rather than integration tests with a web server in them. ObjectStore is eight methods, Fetcher is one, and Reporter is five.

internal/application/service.go
// Fetcher is the remote source boundary used by the service.
type Fetcher interface {
	Fetch(ctx context.Context, request FetchRequest) (*FetchResponse, error)
}

// FetchResponse contains the response fields used by DAC.
type FetchResponse struct {
	NotModified bool
	ETag        string
	Length      int64
	Body        io.ReadCloser
}

The one place the direction is subtle is error detail. A transport failure knows the URL and the HTTP status; the layer that reports it should not have to know which transport produced them. So application declares the interface and httpclient satisfies it:

internal/application/errors.go
// RequestDetail is implemented by a transport error that can name the request
// it failed.
type RequestDetail interface {
	RequestURL() string
	// StatusCode reports the HTTP status, or zero when the request never
	// received a response at all.
	StatusCode() int
}

httpclient asserts the relationship at compile time with var _ application.RequestDetail = (*RequestError)(nil), and the JSON error envelope gets details.url and details.status as data without application importing anything.

Structure

The two project files

The coordinate is the key

Both files key their assets by <namespace>/<name>@<version>. Schema version 2 has no version field inside an entry: it would be a second place to say what the key already says, and the place the two could disagree. There is no migration path from version 1 — a version 1 file is rejected with a message naming the shape the new one takes.

coord.Coordinate implements MarshalText and UnmarshalText, which puts validation exactly at the JSON boundary. Every manifest and lock key is parsed on read, so an invalid coordinate fails at the read that found it rather than at whichever command first tried to use it. And MarshalText validates before writing, because a Coordinate built in memory rather than parsed could otherwise put a key into a file that DAC would refuse to read back — and a file DAC cannot read is a worse failure than a write that refused.

Character rules, and what each one prevents

PartAlphabetReason
namespacelowercase letters, digits, . _ -A label this project chooses. Lowercase because two spellings of one asset would be two assets, and a case difference is the spelling mistake nobody sees.
namelowercase letters, digits, . _ -Same.
versionletters (either case), digits, . _ - +Copied verbatim from whatever the publisher calls a release, so it keeps uppercase and the plus sign build metadata uses.
Every part starts and ends alphanumeric and is at most 64 characters. That rules out the leading dash that reads as a flag wherever a coordinate is a command argument, the trailing dot that reads as a typo, and . and .. outright — and it keeps a value that is simultaneously a map key, a progress-bar label, and an argv element from being unbounded.
Ordering is deliberately meaningless

coord.Compare orders by namespace, then name, then version — all three lexicographically, including the version. DAC has no idea whether 10 follows 9 or whether either is a number. The comparison exists only so that output and file writes are deterministic, and it is documented as something a caller must not read meaning into.

Reading: strict, and strict early

jsonfile.ReadStrict makes three passes' worth of guarantees before a value is returned:

  • A token walk rejects duplicate object keys, which encoding/json would otherwise silently resolve last-wins.
  • DisallowUnknownFields rejects anything the schema does not name, so a typo is a failure rather than a silently ignored setting.
  • A second decode must return io.EOF, rejecting a file with more than one JSON value in it.

Then Manifest.Normalize rewrites every integrity value into the canonical sha256:<hex> form. This must happen before the manifest digest is calculated, or the same manifest written two ways would produce two different manifestDigest values and every lock file would look stale to somebody.

Writing: atomic, paired, and quiet

jsonfile.WriteAtomic writes through a temporary file in the destination directory — chmod, write, Sync, close, rename. The temporary prefix .dac- is exported so that anything sweeping a directory DAC writes into can recognize the files an interrupted write left behind; cache collection uses exactly that.

project.WritePair writes the manifest, then the lock, and restores the manifest — to its previous bytes, or by removing it if it did not exist — when the lock write fails. Two files that disagree is the state every command downstream has to defend against, so the write path refuses to create it.

writeLock compares the encoded bytes against the file on disk and skips a write that would change nothing. Rewriting identical bytes would move the file's modification time for nothing, which anything watching the project directory would read as a change.

Agreement

project.CheckLock compares the manifest digest, the asset count, and each entry. project.Agrees is the per-asset half of the same question, exported because a command deciding which assets it must resolve and a command checking the whole project have to reach the same answer — two answers would mean a lock that one command rewrites and another rejects.

internal/project/project.go
func disagreement(asset Asset, locked LockAsset, exists bool) string {
	switch {
	case !exists:
		return "is not locked"
	case locked.URL != asset.URL:
		return "does not match"
	case asset.Integrity != "" && locked.Digest != asset.Integrity:
		return "does not match its integrity"
	}
	return ""
}

The version is not compared, because it cannot differ: both entries are found by the same coordinate, and the coordinate carries it.

Structure

Identity and version rules

Three checks enforce that a version means one thing. They live in three different places, and where each one lives is the design.

CheckLives inRunsCatches
CheckVersions project.Lock.Validate On every lock read and every lock construction Two versions of one asset naming the same digest. Because it is an invariant of the type, no Lock value anywhere in the program can hold a collision, so no command has to decide what to do about one.
checkRebind application/identity.go Per asset, in reconcile, when the lock already binds that coordinate A locked coordinate resolving to different bytes — an origin that replaced them, or a manifest edited to point that version elsewhere.
checkRetired application/identity.go Over the finished asset set, against the previous lock A new version resolving to bytes a version this project just removed already had. The lock alone cannot see it: editing a version in place takes the old coordinate out of the manifest, so the two never appear together.

Both set-level checks run after every resolution has finished rather than per asset, because both compare one asset against another and neither can be decided while the other resolutions are still in flight.

Where the wording lives

The rule is in project; the instruction is in application. collisionFault translates project.VersionCollisionError into a fault whose message tells an operator what to do, so a lock file with a collision reports "one of these is a label for bytes that already had a version" rather than "the lock file is invalid".

The one command that suspends its rules

dac verify --refresh resolves with AllowRebind set. Leaving the rebind check on would make a refresh fail with version_rebind at the first drifted asset — a second name for the answer this command exists to report, delivered before it could finish collecting it. Verify gathers every drifted asset and reports them together as lock_drift, and writes nothing: a scheduled job that rewrote the lock to match what it found would destroy the evidence on its way to reporting success.

It suspends the publisher pin for the same reason, resolving a pinned asset for the digest its origin now serves rather than against the one the manifest pins. Enforced here, the pin raises content_mismatch from the store before anything has compared the result to the lock — so the refresh would stop at the first drifted asset, report a failed transfer instead of the drift it exists to find, and never reach the assets behind it. Precisely the assets somebody cared enough about to pin would be the ones lock_drift never named. Every command that writes a lock file still enforces the pin: pull --refresh-lock against a moved origin is content_mismatch, and correctly so.

The case DAC declines to refuse

Two versions of one asset served from one URL is not an error. Only one set of bytes is at a URL, so a cold cache can restore only one of them — but the project that pins both and keeps them cached has made a choice DAC has no business overriding. add reports it as sharedSources and continues.

Execution

The resolve ladder

There is no dac lock command. Resolving an asset stores its bytes in the cache, so the command that resolved everything and the command that installed everything were the same command under two names. What remains is one operation — reconcile — and one per-asset routine, resolve.

reconcile: bring the lock into agreement with the manifest

For each coordinate, in parallel: if this is not a refresh and the lock entry still describes the manifest asset, carry it through untouched at status locked — no request at all. That is the property that makes pull usable in a deployment job, and it only survives if assets already locked cost nothing to confirm. Otherwise, call resolve.

One detail hides there: an asset the manifest pins carries no ETag, so a lock entry that kept one from before the manifest pinned it has it cleared on the way through. The ETag was inert — nothing would ever send it — but leaving it would have the lock file contradict what the manifest says about the asset.

resolve: the ladder for one asset

  1. Pinned, not refreshing, and the cache holds that digest

    A publisher digest already settles which bytes are correct, so the answer is on disk. This never confirms the URL still serves those bytes — which is exactly what --refresh-lock trades away. A corrupt object here does not stop the ladder: resolve falls through to the origin and installs good bytes over the bad ones.

    status: cached

  2. Otherwise, decide whether to send a conditional request

    An ETag hint is replayed as If-None-Match only when the asset is unpinned, the old lock entry still matches the manifest, and its object is actually usable. Refresh does not suppress the hint: an origin that answers 304 has confirmed the asset just as well as one that sends the bytes again, and for a large asset that is the difference between a check that runs on a schedule and one nobody runs at all.

  3. The origin answers 304

    The previous lock entry is kept as-is, with a freshly returned ETag recorded if the server sent one.

    status: not_modified

  4. The origin sends bytes

    The body is streamed through the progress reporter into Store.Put, with the publisher digest as the expected digest when there is one and --max-size as the bound when there is not. The object is hashed on the way to disk; nothing is installed until every byte has been checked.

    status: resolved

pull: install what the lock already names

Pull knows the digest and the size before it starts, which lets it take a different, tighter path.

  1. Build the asset view

    One cache lookup answers both "can this command use the object" and "should it say why not", so a warm hit costs one lookup rather than one to decide and another to report.

    status: cached

  2. Take the digest lock, then re-check

    Waiting for the lock takes time during which another process may have installed the object. Checking again under the lock is what makes two concurrent pulls of the same asset cost one download.

  3. Try the distribution directory

    With --distdir, a file named by the locked digest's hexadecimal value is installed straight from disk. That name is the only one a consumer can actually check — DAC used to accept the final URL element, which was a guess and so could not report a mismatch correctly.

    status: distdir

  4. Refuse, if offline

    A missing object is offline_cache_miss. A corrupt object offline gets its own error, because that is a different problem: there is damage to report and no way to repair it here.

  5. Fetch, with a size pre-check

    A known Content-Length that disagrees with the lock fails as content_size_mismatch before the transfer starts. Otherwise the body streams into Store.Put with the exact digest and size required.

    status: downloaded — or repaired, if the object it replaced was corrupt
Status vocabulary

locked (the lock already described it) · resolved (reached the origin and stored bytes) · not_modified (the origin answered 304) · cached (answered from the cache) · downloaded · distdir · repaired. A pull that reconciled an asset in the same run reports resolved as downloaded, because this pull did transfer those bytes — but keeps not_modified distinct from cached, because only the first proves the origin was asked.

Request order

Every fetch goes through the same five gates, in this order:

  1. Rewrite. The canonical URL becomes the request URL. The lock file never sees this.
  2. URL policy on the rewritten target — HTTPS, or HTTP to loopback, or an explicit opt-in. A rewritten target is checked on its own terms rather than on the canonical URL's.
  3. Headers. Accept-Encoding: identity, and If-None-Match when a hint was supplied.
  4. Credentials for the request host, from a helper if one covers it.
  5. Redirects — at most 10, each one re-checked against URL policy and host policy, and re-authorized from scratch.

The stall guard

--timeout is an inactivity timeout, not a deadline. The response body is wrapped in a guard holding a time.AfterFunc timer: every read that returns bytes resets it, and the timer firing cancels the request context. A multi-hour transfer that keeps moving is fine; one that goes quiet for the timeout fails with ErrStalled, which the error layer maps to the code timeout.

The guard also owns the request's cancel function, so closing the body always releases the context — there is no path where a caller closing the response leaks a live request.

Retries

ConditionRetried
HTTP 429, 408, or any 5xxYes
Transport errors (refused connection, reset, DNS failure)Yes
Context cancelled or deadline exceededNo — the caller is already going away
urlpolicy.ErrNotPermitted, including a blocked hostNo — a policy refusal will refuse identically next time
Any other 4xxNo

Backoff honours Retry-After (seconds or HTTP date) capped at 30 seconds; otherwise it is min(2^attempt × 250ms, 8s) plus up to half that again as jitter. The retry loop matches on the transport's own error type, which is why RequestError wraps only at the boundary — wrapping earlier would have every attempt look like a new kind of failure.

Execution

Credential helpers

DAC gets request credentials only from a credential helper. There is no token field in the manifest, no .netrc support, no DAC_TOKEN, and no credential file format. A helper is an executable that DAC runs, hands one request URL, and reads headers back from.

Why a helper and not a config field

A credential's lifetime and refresh policy belong to whatever issues it — a cloud metadata service, a secret manager, an SSO agent — and none of those fit in a committed file. Delegating means DAC stores no secret, transmits no secret between components, and needs no code for expiry, rotation, or revocation. It also means the project files stay safe to commit and to share, which is the property the whole tool is built around.

The protocol

ElementContract
Invocation<command> get
Standard inputOne JSON object: {"uri":"https://files.example.com/geo/database.bin"}
Standard outputOne JSON object: {"headers":{"Authorization":["Bearer ..."]}}
Exit statusZero. Anything else fails the DAC command.
Time limit30 seconds, per invocation.
Output limit1 MiB of stdout, 4 KiB of stderr. Beyond that, writes are accepted and discarded, so the helper never sees a broken pipe.
No helper matchesNo headers. The request goes out unauthenticated rather than failing.
Empty headersTreated as no headers at all.

The header map is map[string][]string, so a helper can return several headers and several values for one header. DAC deletes each named header before adding the helper's values, so a helper's answer replaces rather than appends to anything already on the request.

Selection

A specification is either a bare command or <host>=<command>:

shell
# Every host.
dac pull --credential-helper /usr/local/bin/dac-cred

# One host. A host-specific helper wins over a general one.
dac pull --credential-helper files.internal=/usr/local/bin/dac-cred-internal

# Both: files.internal uses its own helper, everything else uses the general one.
dac pull \
  --credential-helper /usr/local/bin/dac-cred \
  --credential-helper files.internal=/usr/local/bin/dac-cred-internal

Host matching is exact and case-insensitive — no subdomain matching, no wildcards. A helper bound to a host always beats a general helper, whatever order they were given in, so a project can point one registry at a dedicated helper without giving that helper every other request. Among several general helpers, the first wins.

Redirects: the part that matters

Credential leakage across a redirect is the classic failure of every tool that ever sent an Authorization header. DAC's redirect handler does three things in order, on every hop:

  1. Applies URL policy to the new target.
  2. Applies the rewrite config's host policy — but does not rewrite, because a redirect must not start a rewrite chain.
  3. Calls authorize, which deletes Authorization first and then asks the helper again for the new URL.

So a redirect from a private artifact host to a signed CDN URL arrives at the CDN with no credentials, because no helper covers that host — which is the correct outcome and also the one that is easy to get wrong by doing nothing.

internal/httpclient/httpclient.go
// authorize sets the credentials for one request host. It clears any header
// carried over from a previous hop first, so a redirect never forwards one
// host's credentials to another.
func (client *Client) authorize(ctx context.Context, request *http.Request) error {
	request.Header.Del("Authorization")
	header, err := client.options.Credentials.Headers(ctx, request.URL.String())
	if err != nil {
		return err
	}
	if len(header) > 0 {
		for name, values := range header {
			request.Header.Del(name)
			for _, value := range values {
				request.Header.Add(name, value)
			}
		}
	}
	return nil
}

Secrecy discipline

  • Helper stdout is never written to a log, an error message, or a JSON cause. A response that fails to parse reports only credential helper "..." returned invalid JSON — the malformed text, which may well contain the token, is dropped.
  • Helper stderr is included in the failure message when the helper exits non-zero, because that is where a helper explains itself. A helper must therefore never print a secret to stderr.
  • Output is size-bounded before it is buffered, so a runaway helper cannot exhaust memory while DAC waits for it.
  • The 30-second limit is a constant, deliberately not tied to --timeout: that limit covers a multi-gigabyte transfer, and a helper that has not answered in half a minute is stuck.
  • A timeout is distinguished from a cancellation — if the parent context is still live, the error says the helper timed out, naming the command and the limit.

Where helpers apply

add, pull, and verify --refresh — every command that makes a request. --credential-helper is repeatable, and DAC_CREDENTIAL_HELPER sets the same option for a whole job. When no helper is configured at all, the resolver is nil and the header lookup returns immediately, so the unauthenticated path costs nothing.

A minimal helper, end to end

dac-cred-static — a token from a file
#!/usr/bin/env bash
set -euo pipefail

case "${1:-}" in
  get) ;;
  *) echo "unsupported operation: ${1:-none}" >&2; exit 2 ;;
esac

# Read the request. Ignoring it is fine for a single-host helper, but a helper
# bound to several hosts should branch on the URI.
uri=$(jq -r '.uri')

case "$uri" in
  https://files.internal/*)
    token=$(cat /run/secrets/artifacts-token) ;;
  *)
    # No credentials for this host: answer with no headers, not an error.
    echo '{"headers":{}}'; exit 0 ;;
esac

jq -n --arg t "$token" '{headers: {Authorization: ["Bearer \($t)"]}}'
Helper authoring checklist

Answer within 30 seconds · exit 0 on success · write only JSON to stdout · never write a secret to stderr · return an empty headers object rather than failing for a host you do not handle · expect to be called once per request and once per redirect hop, so cache tokens in the helper if minting one is expensive.

Execution

URL policy and the rewrite config

URL policy

urlpolicy is four rules and no configuration:

  • A URL carrying userinfo (https://user:pass@host/) is refused outright — credentials come from helpers, and a URL that carries one would end up in a committed file.
  • HTTPS is always permitted.
  • A non-HTTP(S) scheme is refused.
  • HTTP is permitted for localhost and loopback addresses, or when the caller opted in.

It belongs to neither the project file nor the HTTP client: the manifest applies it when it validates an asset, and the client applies it again to every request and every redirect target. So it sits below both. Its ErrNotPermitted sentinel is what lets the retry logic tell a permanent rejection from a transient network failure.

Rewrite evaluation

A rewrite pattern is a Go regular expression matched against host + path with any query string appended — the same subject Bazel's downloader config uses, so a pattern can key on the host without having to allow for the scheme.

  1. Exactly one rewrite rule may match. Two matches is ErrAmbiguousRewrite, not a silent first-wins. A configuration whose behaviour depends on rule order is a configuration nobody can reason about.
  2. The replacement may omit the scheme, in which case the original URL's scheme is kept.
  3. Host policy is applied to the result, not the original. Allow the host you rewrote to.
  4. Allow beats block, always. The allow list and the block list are scanned separately, so directive order cannot change the decision. A host with no match is allowed. * matches everything; any other pattern matches a host and its subdomains.

Apply returns an error for a blocked host; Evaluate returns the same decision as data, which is what lets dac info print the request URL and the policy result for a host it would refuse to fetch from. Check is the redirect path: host policy only, no rewriting.

Trust model

A rewrite cannot change what DAC accepts. pull still checks the locked digest, so a mirror serving the wrong bytes fails exactly as a corrupted transfer does. The one case with no expected digest is resolving an asset that carries no integrity value — there is nothing to check against yet, so a rewrite config is trusted input in precisely the same way a manifest URL is. Treat it as part of the project, not as a runtime setting.

Storage

The object cache

The cache is keyed by digest and nothing else. Several versions of an asset sit in it side by side with no arrangement needed, two assets that resolved to the same bytes cost one object between them, and there is no layout to migrate when the project schema changes.

layout
<cache>/blobs/sha256/<hex>         the object, mode 0444
<cache>/blobs/sha256/<hex>.meta    the sidecar
<cache>/locks/<hex>.lock           the per-digest process lock
<cache>/tmp/download-*             in-flight downloads

The root resolves from --cache-dir, then DAC_CACHE_DIR, then XDG_CACHE_HOME/dac, then $HOME/.cache/dac — and if none of those yields an absolute path, the command fails saying so rather than guessing.

The problem the sidecar solves

A content-addressed name is a claim about content, not a fact. Checking the claim means hashing the whole object — and an asset can be gigabytes while dac path runs in the middle of a build. Hashing on every read is unaffordable; trusting the filename is exactly the guarantee DAC exists to make.

So each object carries a sidecar recording the size and modification time it had at install. A stat that still matches means nothing has written to the object, and DAC uses it without reading it. Anything else — an object edited in place, a truncated one, a restored backup, a cache written by an older DAC — costs one hash, after which the object is either recorded as good or reported as corrupt.

The key consequence

The object's own timestamp is the evidence, so DAC never touches it after install. The liveness signal that garbage collection needs lives in the sidecar instead, and a cache hit refreshes the sidecar's timestamp. That one split is why the cache can be both tamper-evident and collectable without either mechanism destroying the other.

The trust ladder

  1. This process already hashed these exact bytes

    A sync.Map on the store memoizes digest → file information. Without it a single command would hash the same object several times: pull stats an object to decide whether it needs it, again under the digest lock, and again to build its result. It also keeps a read-only cache — where no sidecar can ever be written — down to one hash per object.

    cost: one map lookup

  2. The sidecar describes the object

    Sidecar version, size, and modification time in nanoseconds must all match. A sidecar from an unsupported version describes nothing, which sends the object down the hashing path and rewrites the sidecar in the current form — that is how a cache from an older DAC migrates.

    cost: one stat

  3. Hash the object

    On a match, write the sidecar and remember it. On a mismatch, raise CorruptError naming the digest expected, the digest found, and the path.

    cost: one full read

hashFile takes its file information from the open descriptor, not from the path. An install renames a new object over the old one, so a path stat taken after the hash could describe bytes the function never read — and recording it would mark an unverified object as verified.

Store.Verify, which backs dac cache verify, deliberately ignores both the memo and the sidecar. Those exist so ordinary commands can avoid reading an object they have reason to trust, and an explicit check that trusted them would only ever confirm its own bookkeeping.

Installing an object

  1. Create a temporary file under <cache>/tmp/download-*.
  2. Wrap the reader in a limit — the expected size when known, otherwise --max-size — reading one extra byte, so an oversized response cannot look complete.
  3. Copy through an io.MultiWriter into the file and a SHA-256 hasher at once.
  4. Compare size and digest. An overrun of a known size is a content failure; an overrun of --max-size is a limit the operator chose, and gets a different error.
  5. Sync, chmod 0444, close.
  6. Take the digest lock, unless the caller already holds it, and rename into place.
  7. Write the sidecar and record the result.

The install is unconditional — it does not skip an object that already exists at the path. These bytes have just been hashed, so they are known good, while an object already there is only known to have the right name, which is exactly the claim this store no longer takes on trust. Renaming over it repairs a corrupt object at no extra cost.

A failed sidecar write after a successful install is fatal. The alternative is a cache that silently re-hashes a multi-gigabyte object on every read for the rest of its life, and a filesystem that has just accepted the object but refuses a two-hundred-byte sidecar has a problem worth reporting. The object survives the error, so the next command repairs it.

Locking

Each digest has a lock file taken with flock(LOCK_EX), polled every 25 ms and abandoned on context cancellation. Concurrent DAC processes therefore cannot install the same object at the same time, which is what makes a shared cache on a build machine safe. Release always releases: closing the file drops the lock even when the explicit unlock fails, so a returned error only ever describes a file descriptor the caller has finished with, never a lock that is still held.

Collection

dac cache gc ages an object by its sidecar timestamp, which every cache hit refreshes. It also removes temporary files abandoned by an interrupted download and sidecars whose object is gone — collection removes an object and its sidecar together, so one that survives alone describes an object something outside DAC deleted. Each removal happens under that object's digest lock, and the timestamp is re-checked under the lock, because waiting for it takes time during which another process may have used the object.

That includes the sidecar sweep, which works from a directory listing taken before any of the collection. A sidecar can lose its object twice over — once because this run collected the pair, and once because something outside DAC removed the object — and only the second is damage worth reporting, so the sweep is told what this run took. It also leaves a sidecar the cutoff has not reached, exactly as it leaves a temporary file that new: one written while the run was walking the directory belongs to an install happening right now, and taking it would cost the next command a full re-hash of an object nothing had been in doubt about.

Lock files are never collected

Unlinking a lock file that another process holds would let a later process take the same lock through a new inode — two processes holding "the same" lock and neither of them wrong. Lock files are tiny and bounded by the number of distinct digests the machine has ever seen, so they stay.

What each command does with a corrupt object

CommandBehaviourReasoning
dac pathRefuses.It cannot do anything about the damage, and handing back bytes that fail their own claim is worse than handing back nothing.

dac pull --offlineFails with cache_object_corrupt.Damage to report, and no way to repair it here.

The split is one function pair: cached reports a corrupt object as an error, and usable treats it as absent. Commands that can fetch the object again call usable; commands with no such recourse call cached and report.

Storage

Cache bundles

A bundle is a tar file borrowing two ideas from the OCI image layout: an index.json at the tar root, and content-addressed blob paths. It does not borrow OCI's manifest indirection, because a cache bundle has nothing to describe that a flat item list cannot.

index.json
{
  "schemaVersion": 2,
  "items": [
    {
      "coordinate": "backend-app/geo-database@2026.08",
      "sourceUrl": "https://example.com/geo/2026.08/database.bin",
      "file": "blobs/sha256/9c01741d92a2f71fb069201ab22b458b72400a2b884394ff772c4c07fc031820",
      "digest": "sha256:9c01741d92a2f71fb069201ab22b458b72400a2b884394ff772c4c07fc031820",
      "size": 4194304
    }
  ]
}

An item names the asset by its whole coordinate rather than by parts: the parts exist for a consumer reading a command result, and an index DAC writes and reads back has no use for three fields that could contradict each other.

Writing

  • The whole archive is written through a temporary file and one rename, like every other file DAC writes.
  • The index goes first, then each unique blob — two assets that resolved to one object share one blob, which is what makes a bundle for a project vendoring the same file under two namespaces no larger than one that does not.
  • Tar headers are fixed: USTAR format, mode 0444, modification time at the Unix epoch. The same object set produces the same bytes.
  • Each blob is hashed while it is written and compared to the locked digest, so a corrupt object is caught during export rather than during import on a machine that cannot fix it.
  • A long copy checks the command context between blocks, so cancellation is prompt.

Reading

import validates the schema version, every coordinate, a non-empty source URL, a non-negative size, and — critically — that each item's file equals the path derived from its own digest. It rejects duplicate coordinates and inconsistent metadata for one file, and it caps the index at 16 MiB. The whole index is validated before a single object is installed, and each object is installed through the same Put path as a download, so it is hashed and checked on the way in. import reads no project files, so one bundle can seed several checkouts.

Contracts

Errors and output

One error type

internal/fault/fault.go
// Error contains a stable code and a user message.
type Error struct {
	Code    string
	Message string
	Details map[string]any
	Cause   error
}

Code and Message are stable enough to branch on, which is exactly why neither says anything specific about a failure: "The asset request failed" is equally true of a refused connection, a 404, and an expired certificate. Cause carries the part an operator acts on, and Details repeats the useful parts of it as data — url and status for a request failure, expected and actual digests for a content failure, locked and resolved digests for a version_rebind, the two versions and the shared object for a version_collision.

Error() trims the message's full stop before appending the cause, because messages are sentences and causes are clauses, and joining them with the stop still in place reads as a typo. fault.As maps any unrecognized error to internal_error, so every failure leaves the program with a code.

At the parallel boundary, withAsset clones the details and adds the coordinate, so every per-asset failure names its asset without each call site remembering to.

Versioning the contract

The envelope carries outputVersion. Version 2 moved info's counters into a summary object, dropped allowedCount, and added cause to every error. Version 3 gave every asset a coordinate and a namespace alongside its name and version, dropped replaced from an add result because adding a version no longer retires one, and added siblings, sharedSources, and remaining so that a command changing one version says what happened to the others.

Exit status is three values: 0 success, 1 the command failed, 2 DAC rejected the arguments. A write failure on the result itself also exits 1, without trying to write a second document explaining that the first one could not be written.

Contracts

Concurrency model

Within one command

internal/application/parallel.go
func parallel[K fmt.Stringer, T any](ctx context.Context, limit int, names []K,
	operation func(context.Context, K) (T, error)) ([]T, error) {

	group, runCtx := errgroup.WithContext(ctx)
	group.SetLimit(max(limit, 1))
	results := make([]T, len(names))
	for index, name := range names {
		group.Go(func() error {
			// Another asset has already failed and cancelled the run. Report
			// nothing for this one: a column of cancellations would bury the
			// single failure that caused them.
			if runCtx.Err() != nil {
				return nil
			}
			value, err := operation(runCtx, name)
			if err != nil {
				return withAsset(err, name.String())
			}
			results[index] = value
			return nil
		})
	}
	// ...
}

Results are written into a pre-sized slice by index, so there is no mutex and the output order is the coordinate order regardless of completion order. The first failure cancels the rest through errgroup's context.

The subtlety worth naming: an operation whose context is already cancelled belongs to that first failure, not to a problem of its own. Callers check ctx.Err() before reporting anything to the progress reporter, because an asset cut short mid-transfer would otherwise surface a message describing a completely different asset's failure. After Wait, parallel re-checks the parent context so a cancelled command reports cancellation rather than an empty success.

Across processes

Two DAC processes sharing a cache — two CI jobs on one runner, two Docker builds against one cache mount — coordinate through the per-digest flock. The install path takes it around the rename; the pull path takes it around the entire decide-then-download sequence and re-checks the cache under it, so the second process gets a cache hit rather than a duplicate download. Collection takes it around each removal.

cache.Store must not be copied: its sync.Map memo is what keeps a command from hashing the same object repeatedly, and a copy would silently start again from nothing.

Contracts

Decision log

The choices that shaped everything above, each with the consequence it buys.

Return a path; never unpack, install, or run

Because
Every consumer wants something different from a tarball, and a fetcher that unpacks has to grow flags for strip-components, overwrite policy, and ownership — none of which it can get right for everyone.
Buys
DAC works behind make, Docker, Bazel, and Ansible without any of them agreeing with each other, and its blast radius is one directory of read-only files.

The version is part of the key, not a field

Because
A version field inside an entry is a second place to say what the key already says, and therefore the place the two can disagree.
Buys
A project holds several versions of an asset naturally; editing a version in place cannot quietly redefine the asset that was already there; there is nothing to keep in sync.
Costs
A hard break from schema version 1, with no migration — the file is rejected with a message naming the new shape.

Two local rules about versions, and no version semantics at all

Because
Choosing versions is a package manager's job. Guaranteeing that the version you wrote down is the version you get is not, and nobody else was doing it.
Buys
No ordering, no ranges, no latest, no resolution algorithm — and both rules are decidable from the project's own two files, with no network and no registry.

A sidecar records the object's stat at install

Because
A content-addressed name is a claim, and checking it means hashing gigabytes in the middle of a build. Trusting the filename gives up the guarantee; hashing every time gives up the performance.
Buys
Ordinary commands verify with one stat and catch every case that actually happens — edited in place, truncated, restored from backup. dac cache verify covers the rest at the cost of reading everything.
Follows
The object's own timestamp becomes evidence, so liveness had to move into the sidecar — which is why a cache hit touches the sidecar and never the object.

Install unconditionally, even over an existing object

Because
Freshly hashed bytes are known good; an object already at that path is only known to have the right name.
Buys
Corruption repair for free — the pull that noticed the damage is the command that fixes it.

A per-digest flock, and lock files are never deleted

Because
A global cache lock would serialize unrelated downloads. And unlinking a lock another process holds lets a later process take the same lock through a new inode.
Buys
Safe shared caches on build machines, with concurrency bounded by assets rather than by the cache.
Costs
Unix only — made explicit with a build constraint so a Windows build fails at proclock rather than somewhere deep in the cache.

Credentials come only from a helper process

Because
Token lifetime, refresh, and revocation belong to whatever issues the token, and none of that fits in a committed file.
Buys
DAC stores no secret and logs no secret; project files stay safe to commit; and clearing credentials per redirect hop is a rule in one function rather than a property of a config format.

Rewrites are separate from the manifest

Because
A manifest records where an asset comes from upstream. Where this deployment fetches it from is one site's topology, and putting it in the manifest spreads that topology across every repository that uses the asset.
Buys
The same commit builds on a laptop with open egress and on a fleet that can reach exactly one host. The lock file stays canonical, so a digest recorded behind a mirror still means something upstream.

ETags only for unpinned assets

Because
A publisher digest already settles which bytes are correct. Revalidating against a weak cache header adds a request and answers a question already answered.
Buys
A pinned asset is answered from the cache or downloaded outright, and its lock entry carries no etag field to go stale.

--max-size bounds only unknown-size responses

Because
When the size is known, it is the limit. A separate ceiling then only exists to stop a runaway stream, not to express a policy about how large assets may be.
Buys
A default of 2 GiB that is a real guard rather than a knob generating questions — and a distinct error for "the operator chose this limit" versus "the content is wrong".

Stable codes, specific causes

Because
A message you can branch on cannot also be a message that diagnoses, and a tool that mixes the two ends up with neither.
Buys
Scripts branch on code; humans read cause; machines read details. A CI failure someone can read, rather than one someone has to reproduce by hand.

No dac lock command

Because
Resolving an asset stores its bytes, so the command that resolved everything and the command that installed everything were one command under two names.
Buys
One mental model: pull installs, and lock flags say whether it may write. Nothing writes the lock file without being asked — add and remove maintain it because they are already changing the project.

Constraints and dependencies

platform

Unix, Go 1.26

proclock carries //go:build unix. There is no Windows build and no plan for one: the cache's correctness rests on flock.

dependencies

Three direct, all small

urfave/cli/v3 for the command tree, vbauerster/mpb/v8 for concurrent progress bars, golang.org/x/sync for errgroup. Everything else is the standard library.

testing

Fakes at the ports

Command tests substitute a fake store and fetcher rather than standing up a server; internal/projecttest shares project fixtures. mise run check is go vet plus the full suite under -race.

compatibility

Four version numbers

Application 6.0.0, manifest and lock schema 2, output contract 3, bundle schema 2, sidecar 1. Each moves for its own reasons and each rejects what it does not understand.
