DAC

DAC locks remote files and keeps them in a local content-addressed cache. It gives deployment and infrastructure tools one stable way to fetch data files, policy bundles, provider binaries, and similar build inputs — and then it gets out of the way.

go 1.26 unix only sha-256 content addressed manifest + lock v6.0.0 · output v3

Overview

What DAC is

A build needs files that are not code: a GeoIP database, a model checkpoint, an OPA policy bundle, a vendored toolchain tarball. The usual answer is a curl in a Dockerfile, and it fails in the same three ways every time — the URL moves, the bytes change without the name changing, and nobody can tell you what the last green build actually downloaded.

DAC replaces that curl with two committed files and one command. You name an asset by a coordinate, DAC resolves it once, records the exact digest, and every later machine gets those bytes or a hard failure. Nothing in between.

The boundary

DAC does not unpack or install assets. It returns the verified cache path and stops. The calling script decides what to do with it — which is why DAC fits behind make, docker build, Bazel, Ansible, or a shell script without any of them having to agree with each other.

shell
dac init
dac add backend-app/geo-database@2026.08 \
  https://example.com/geo/2026.08/database.bin --pin
dac pull

# DAC returns a path. Extraction belongs to whatever consumes it.
geo_database="$(dac path backend-app/geo-database@2026.08)"
tar -xzf "$(dac path tools/toolchain@1.4)" -C vendor/toolchain

add resolves the asset and updates both project files. Commit dac.json and dac-lock.json. From then on, dac pull in CI reproduces the project as committed — and uses a matching cache object with no network request at all.

The coordinate

An asset is named <namespace>/<name>@<version>. All three parts are required and together they are the whole identity. A namespace lets backend-app/database and frontend-app/database be two different files rather than an argument about who owns the name. A namespace is a grouping label: nothing owns one, nothing registers one, and two projects using the same namespace is not a conflict.

A namespace and a name take lowercase letters, digits, and . _ -. A version also takes uppercase and +, because it is copied from whatever the publisher calls a release. Every part starts and ends alphanumeric, and none exceeds 64 characters.

The two files

dac.json — source intent
{
  "schemaVersion": 2,
  "assets": {
    "backend-app/geo-database@2026.08": {
      "url": "https://example.com/geo/2026.08/database.bin",
      "integrity": "sha256:optional-publisher-digest",
      "allowInsecureHttp": false
    },
    "backend-app/geo-database@2026.09": {
      "url": "https://example.com/geo/2026.09/database.bin"
    }
  }
}
dac-lock.json — resolved bytes
{
  "lockVersion": 2,
  "manifestDigest": "sha256:...",
  "assets": {
    "backend-app/geo-database@2026.08": {
      "url": "https://example.com/geo/2026.08/database.bin",
      "digest": "sha256:...",
      "size": 4194304,
      "etag": "\"4f12535150d37a844beafcc03868e865\""
    }
  }
}

The lock carries a manifestDigest, so a lock file either describes the manifest beside it or it does not — there is no partial agreement. Commit both. A hand edit to dac.json resolves nothing until you ask for it with dac pull --update-lock.

The cache

Objects live in a shared per-machine cache keyed by digest and nothing else, so several versions of an asset sit side by side with no arrangement needed, and two assets that resolved to the same bytes cost one object between them. The default location is the XDG cache directory; --cache-dir or DAC_CACHE_DIR moves it, and dac cache dir prints where it resolved to.

cache layout
<cache>/blobs/sha256/<digest>
<cache>/blobs/sha256/<digest>.meta

The sidecar is what keeps dac path from hashing a multi-gigabyte file in the middle of a build while still refusing to hand back bytes it cannot vouch for. That mechanism is covered in the architecture document.

Capabilities

Features

identity

Coordinates, not filenames

Namespace, name, and version are the key of both project files. A project holds as many versions of an asset as it names.

reproducibility

A version means one thing

Once a coordinate is locked to a digest, nothing rewrites it. Drift fails the command instead of silently changing the build.

integrity

Verified paths only

dac path returns an object that still holds the bytes DAC installed, or it refuses. Corruption is reported, never handed back.

speed

Warm pulls cost nothing

An asset the lock already describes and the cache already holds needs no request. A whole dac pull can be zero packets.

freshness

ETag revalidation

An unpinned asset records the origin's ETag and replays it as If-None-Match; a 304 confirms it without a transfer.

trust

Publisher pinning

--pin records the resolved digest as integrity. DAC also reads the SRI sha256-<base64> spelling and normalizes it.

secrets

Credential helpers

No tokens in the manifest, the lock, or a config file. A helper program answers per request, per host, and is re-asked after every redirect.

topology

Rewrite config

Send requests to a mirror without editing a single manifest, and allow/block hosts outright. Canonical URLs stay canonical.

isolation

Bundles and distdir

export/import move a whole locked cache across an air gap as one tar; --distdir installs from a directory of digest-named files.

automation

Machine output

--json writes one versioned envelope with a stable error code, a human cause, and structured details.

maintenance

Cache hygiene

cache gc collects by last use, cache verify --repair hashes objects and removes the ones that no longer match.

throughput

Parallel and safe

Assets download concurrently, and concurrent DAC processes coordinate through a per-digest lock, so shared runners cannot corrupt each other.

Guarantees worth stating plainly

  • A plain dac pull never writes the lock file and refuses one that does not describe the manifest.
  • A failed dac add changes neither project file.
  • dac verify --refresh writes nothing, ever — it reports and exits 1.
  • DAC requires HTTPS. Plain HTTP is allowed only for loopback hosts, or with an explicit opt-in per asset.
  • Credentials are cleared on every redirect and re-requested for the new host.
  • Project files are written with atomic renames, and unknown fields, duplicate keys, and unsupported schema versions are rejected on read.

The core rule

What a version means

A version is part of an asset's identity, not a field describing it. Two rules follow from that, and between them they are the whole of what DAC knows about versions.

Rule 1 — a locked coordinate always names the same bytes

Once the lock binds backend-app/database@1.0.0 to a digest, nothing rewrites that digest. An origin that replaced what it serves behind a stable URL, and a manifest edited to point one version somewhere else, both fail with version_rebind, which reports the digest the lock holds and the digest that arrived. The way forward is a new version. --rebind exists for the project that genuinely tracks a rolling source and has decided to accept the change; it writes the lock file, so it only works alongside --update-lock or --refresh-lock.

Rule 2 — two versions of one asset never name the same bytes

Adding backend-app/database@2.0.0 with the source @1.0.0 already had resolves to bytes that already have a version, and fails with version_collision. Editing a version in place fails the same way: the old coordinate leaves the manifest, so the two never appear together, but the previous lock file still remembers what it named.

Neither rule reads anything but the project's own two files. DAC does not order versions, compare them, parse them, or ask an origin what exists — deciding which version to use is a package manager's job. This is only about the version you already wrote down meaning what it says.

Two versions of one asset served from one URL is not refused. Only one set of bytes is at a URL, so a cold cache can restore only one of them, and add reports that in sharedSources rather than deciding it for you.

Fit

Where it fits

DAC is for build inputs that are files, published by someone else, and too large or too licence-encumbered to commit. If a package manager already handles it, use the package manager.

Reference databases

GeoIP and ASN databases, timezone data, spam lists, vulnerability feeds — files that ship on a calendar and get baked into images.

Model artifacts

Checkpoints, tokenizers, embeddings, ONNX exports. Large, immutable, and exactly the thing you want a digest on.

Policy bundles

OPA bundles, Falco rule sets, CA root stores, WAF signature packs — governance inputs that must be auditable back to a byte.

Toolchains & binaries

Vendored SDK tarballs, Terraform providers, protoc plugins, linters. Pin them per project instead of per Dockerfile.

Firmware & images

Device firmware blobs, base rootfs tarballs, VM images that a deployment job stages onto hardware.

Test corpora

Golden files, fuzzing corpora, recorded fixtures. Too big for git, and a silent change turns into a mystery test failure.

Licensed datasets

Vendor data behind an authenticated URL, fetched with a credential helper so no token lands in the repository.

Air-gapped delivery

Build the bundle once on a connected machine, carry one tar across the boundary, pull offline on the other side.

Multi-tool builds

Anything where make, Docker, Ansible, and a deploy script all need the same file and must agree on which one.

Not a fit

Application dependencies with a resolver (npm, Go modules, pip), anything needing version ranges or transitive resolution, anything that must be unpacked or installed by the fetcher, mirroring an entire upstream repository, or artifacts you publish yourself and could simply address by digest in a registry.

Practice

Playbooks

Nine patterns, each one a complete recipe. They assume the two project files are committed and a dac binary is on PATH.

01

Fetch assets into a Docker image

Bake locked build inputs into an image without shipping the cache, the manifest, or a network dependency into the runtime layer.

The shape is a dedicated assets stage that owns the fetch, a BuildKit cache mount that keeps the content-addressed store out of the image layers, and a final stage that copies only the extracted result.

Dockerfile
# syntax=docker/dockerfile:1.7

# ---- assets: resolve every build input from the lock file --------------------
FROM debian:bookworm-slim AS assets
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates \
 && rm -rf /var/lib/apt/lists/*
COPY --from=ghcr.io/example/dac:6 /usr/local/bin/dac /usr/local/bin/dac

WORKDIR /project
# Copying only the project files means this layer is invalidated exactly when
# the lock file changes -- not when application source changes.
COPY dac.json dac-lock.json ./

# The cache mount keeps the object store out of the image and makes a rebuild
# that changed nothing cost zero downloads. DAC takes a per-digest lock, so the
# default sharing=shared is safe for parallel builds on one machine.
RUN --mount=type=cache,target=/root/.cache/dac \
    dac pull --progress=false \
 && install -D "$(dac path backend-app/geo-database@2026.08)" /out/geo/database.bin \
 && mkdir -p /out/policy \
 && tar -xzf "$(dac path platform/opa-bundle@1.12.0)" -C /out/policy

# ---- runtime -----------------------------------------------------------------
FROM gcr.io/distroless/base-debian12
COPY --from=assets /out/geo/database.bin /var/lib/app/geo/database.bin
COPY --from=assets /out/policy           /etc/app/policy
COPY app /usr/local/bin/app
ENTRYPOINT ["/usr/local/bin/app"]

Why each piece is there

plain dac pull
Refuses a lock file that does not describe the manifest. Someone who edits dac.json without locking it breaks the image build loudly instead of shipping something nobody chose.
cache mount
The cache never becomes a layer, so the image does not carry a second copy of every asset, and a rebuild reuses objects across builds of unrelated images.
dac path
Returns a path only for an object that still holds the bytes DAC installed. A truncated or edited cache object fails the build here rather than inside the running container.
--progress=false
BuildKit logs are not a terminal, so DAC would emit start/finish lines per asset. Turning it off keeps the log short; leave it on if you want per-asset timing.

Fully hermetic variant

If the build must make no requests at all, pre-warm the cache mount in an earlier step or bind-mount a populated cache, then forbid the network:

Dockerfile fragment
RUN --mount=type=cache,target=/root/.cache/dac \
    --network=none \
    dac pull --offline --progress=false \
 && install -D "$(dac path backend-app/geo-database@2026.08)" /out/geo/database.bin

--offline makes a cache miss a hard failure with the code offline_cache_miss, which is what you want: a hermetic build that quietly reached the internet is not hermetic.

Alternative: keep the asset out of the image

For a large database that changes on its own schedule, copy the object into a volume at deploy time instead of into the image. The image stays small and the same DAC coordinate names what the volume should contain: dac pull && install -D "$(dac path backend-app/geo-database@2026.08)" /srv/data/geo.bin.

02

CI pipeline with a warm cache

Make repeat builds fetch nothing, and make an unlocked manifest fail the job rather than the release.

.github/workflows/build.yml
name: build
on:
  push:
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # The lock file names every digest this build needs, so it is the exact
      # cache key: a hit means every object is already on disk.
      - name: Restore the DAC object cache
        uses: actions/cache@v4
        with:
          path: ~/.cache/dac
          key: dac-${{ runner.os }}-${{ hashFiles('dac-lock.json') }}
          restore-keys: dac-${{ runner.os }}-

      - name: Check that the project files agree
        run: dac verify

      - name: Fetch build inputs
        run: dac pull --progress=false --concurrency 8

      - name: Build
        run: make build GEO_DB="$(dac path backend-app/geo-database@2026.08)"
  1. Key the cache on the lock file. Content-addressed objects never change under a digest, so a hit is always valid; restore-keys gives a partial hit when one asset changed, and pull fetches only that one.
  2. Run dac verify first. It reads two files, makes no requests, and separates "somebody forgot to lock" from "the download failed" before a single byte moves.
  3. Raise --concurrency on a big project. The default is 4; runners with real bandwidth do better at 8–16. The first failure cancels the rest, so a broken origin does not cost you the whole timeout.
  4. Never run --update-lock in a normal CI job. A job that rewrites the lock is a job that decides what your build uses. Keep that on a human's branch, or on a deliberate, separate workflow.
Self-hosted runners

Point every job at one persistent cache directory with DAC_CACHE_DIR and let them share it. Concurrent DAC processes coordinate with a per-digest lock, so two jobs pulling the same asset at the same time is safe. Pair it with the hygiene playbook so the directory does not grow forever.

03

Scheduled drift watch

Find out that an origin replaced the bytes behind a stable URL — without changing what your project uses.

dac verify --refresh resolves every asset, writes nothing, and exits 1 with the code lock_drift and the drifted asset names when the origins no longer serve the locked bytes. Run it nightly. Resolving an asset means downloading it, so a refresh also warms the cache on its way past.

scripts/drift-watch.sh
#!/usr/bin/env bash
set -euo pipefail

if dac verify --refresh --json > verify.json; then
  echo "Every origin still serves the locked bytes."
  exit 0
fi

code=$(jq -r '.error.code' verify.json)

if [ "$code" != "lock_drift" ]; then
  # A real failure: an unreachable origin, a blocked host, a bad lock file.
  jq -r '"\(.error.code): \(.error.cause)"' verify.json >&2
  exit 1
fi

echo "The following origins changed what they serve:"
jq -r '.error.details.assets[]' verify.json

# Turn it into whatever your team reads: an issue, a Slack message, an alert.
exit 1
What to do about drift

Drift is a decision, not a defect, which is why verify refuses to fix it. Either the publisher released something new — add a new version and retire the old one (playbook 7) — or the URL is genuinely rolling, in which case dac pull --refresh-lock --rebind accepts the new bytes under the same coordinate and records them in a lock diff a human can review.

Note what this cannot tell you: nothing reports that version 2026.09 exists upstream. DAC does not track releases. Bumping a version stays a manual edit.

04

Air-gapped or isolated build

Move a complete, verified set of build inputs across a network boundary as one file.

shell — connected side
# From a checkout of the exact commit the isolated machine will build.
git checkout v1.8.0
dac pull
dac export --file dac-cache.tar

# The bundle carries every locked object plus an index naming each coordinate,
# source URL, digest, and size. Two assets that resolved to the same bytes
# share one blob, so the bundle is no larger than the object set.
sha256sum dac-cache.tar
shell — isolated side
dac import --file dac-cache.tar   # validates index, paths, sizes, and digests
dac pull --offline                # installs from the cache; no requests at all
make build

import checks the index, the entry type, the path, the size, and the digest, and rejects an invalid bundle before it installs anything. It does not read the project files, so one bundle can seed several checkouts. export refuses if any locked object is missing or corrupt — a bundle is the one artifact that would carry cache damage onto a machine with no way to tell where it came from.

Variant: a distribution directory

If your transfer mechanism is a mounted share rather than a tar, --distdir installs locked assets from a directory before requesting them. Each file must be named by its SHA-256 hexadecimal digest — the only name a consumer can actually check.

shell
# Populate the share, naming each file by its digest.
for file in /staging/*; do
  install -D "$file" "/mnt/dist/$(sha256sum "$file" | cut -d' ' -f1)"
done

# On the isolated machine:
dac pull --distdir /mnt/dist --offline

Variant: a dacpack, when the far side is not DAC

A bundle names everything by digest, which is exactly what DAC needs and exactly what nothing else can read. When the thing receiving the archive is a person, an installer, or a build step that switches on a file extension, dac pack writes the same assets materialized under the names their origins gave them.

shell — connected side
dac pull
dac pack                          # writes ./dac.dacpack; --file names another

tar -tf dac.dacpack
# index.json
# assets/java/sdk/11/jdk-11.tar.gz
# assets/java/sdk/17/jdk-17.tar.gz
shell — isolated side
dac unpack                        # installs the objects into the local cache
dac pull --offline

# Or, for a consumer that has never heard of DAC:
tar -xf dac.dacpack -C /opt/inputs

The coordinate supplies the directories, because two versions of one asset almost always share a file name and two assets easily can — keyed on the name alone, the second file would silently overwrite the first. index.json maps each file back to its cache object, which is what unpack reads.

Two costs come with materializing. Two coordinates that resolved to the same bytes are one blob in a bundle and two files in a dacpack, so a project whose assets overlap packs larger than it exports. And the paths now carry names a remote server chose, so unpack recomputes every path from the coordinate it belongs to and refuses an index that claims anything else; a file name that is not a single safe path element is refused outright. Objects land under their digests in any case, so a dacpack never decides where anything on the filesystem is written.

05

Assets behind a private artifact host

Fetch authenticated URLs without putting a token in the repository, the environment, or a log.

DAC gets request credentials only from a credential helper: a program DAC runs as <command> get, hands one request URL on standard input, and reads headers back from standard output. Nothing about the token lives in dac.json, dac-lock.json, or any DAC config.

/usr/local/bin/dac-cred-artifacts
#!/usr/bin/env bash
# DAC invokes this as: dac-cred-artifacts get
set -euo pipefail
[ "${1:-}" = "get" ] || { echo "unsupported operation" >&2; exit 2; }

request=$(cat)                        # {"uri":"https://files.internal/geo.bin"}
uri=$(printf '%s' "$request" | jq -r '.uri')

# Mint or read a short-lived token however your platform does it.
token=$(vault read -field=token "secret/artifacts?uri=$uri")

jq -n --arg t "$token" '{headers: {Authorization: ["Bearer \($t)"]}}'
shell
# One host, one helper. A host-specific helper wins over a general one.
dac pull --credential-helper files.internal=/usr/local/bin/dac-cred-artifacts

# Several hosts: repeat the flag.
dac pull \
  --credential-helper files.internal=/usr/local/bin/dac-cred-artifacts \
  --credential-helper models.vendor.com=/usr/local/bin/dac-cred-vendor

# For a whole CI job, set it once.
export DAC_CREDENTIAL_HELPER=/usr/local/bin/dac-cred-artifacts
dac pull
Two rules for helper authors

A helper has 30 seconds to answer, and a failing helper fails the command. DAC never writes helper output to a log or an error message — but it does include a failing helper's standard error in the failure message, so never print a secret there.

DAC clears credentials on each redirect and asks again for the new host, so one host's credentials never reach another — including a redirect to a signed CDN URL that needs no credentials at all. Within one transfer a helper is asked once per URL, so the range requests a split download is made of do not start it again for every 8 MiB; if an origin then answers 401 or 403, DAC forgets what it was holding, asks once more, and retries. The full protocol, selection rules, and limits are in the architecture document.

06

Egress lockdown and internal mirroring

Send every request through an internal mirror and refuse anything else, without editing a single manifest.

A manifest records where an asset comes from upstream. A rewrite config decides where DAC actually sends the request. The manifest and the lock file keep the canonical URL, so the same repository works on a laptop with open egress and on a build fleet that can only reach one host.

dac-rewrite.cfg
# Block every host that no allow rule permits.
block *

# The mirror, and the one origin allowed through directly.
allow artifacts.internal
allow releases.internal

# Send vendor downloads to the mirror. The pattern is a Go regular expression
# matched against "host/path" with any query string appended.
rewrite ^vendor\.example\.com/(.*)$   https://artifacts.internal/vendor/$1
rewrite ^objects\.githubusercontent\.com/(.*)$ https://artifacts.internal/gh/$1

Save it as dac-rewrite.cfg beside the manifest and DAC loads it automatically. DAC_REWRITE_CONFIG points at a different file, and that file must exist. --no-rewrite disables the whole config for one command.

Rules that matter in practice

  • DAC applies one rewrite before it checks allow and block, so allow the rewritten host, not the original.
  • A URL matching two rewrite rules is an error, not a race. Keep patterns disjoint.
  • An allow match overrides all block matches, and directive order does not change that. A host with no match is allowed; * matches every host; other patterns match a host and its subdomains.
  • Redirect targets get the same host policy but are never rewritten — a redirect must not start a rewrite chain.
  • A replacement without a scheme keeps the original URL's scheme. Add a bare allow_insecure_http directive to permit plain HTTP for rewritten URLs.

Check the result before you trust it — dac info shows the source URL, the request URL, and the host policy result for each asset, and makes no network request:

shell
dac info backend-app/geo-database@2026.08
output
backend-app/geo-database@2026.08
source: https://vendor.example.com/geo/2026.08/database.bin
request: https://artifacts.internal/vendor/geo/2026.08/database.bin
policy: allowed
lock: current
cache: cached
integrity: sha256:9c01741d92a2f71fb069201ab22b458b72400a2b884394ff772c4c07fc031820
digest: sha256:9c01741d92a2f71fb069201ab22b458b72400a2b884394ff772c4c07fc031820
size: 4.0 MiB
path: /home/build/.cache/dac/blobs/sha256/9c01741d...
A rewrite cannot change what DAC accepts

pull still checks the locked digest, so a mirror that serves the wrong bytes fails exactly as a corrupted transfer does. The exception is resolving an asset that has no integrity value yet: there is no expected digest, so a rewrite config is trusted input in the same way a manifest URL is.

07

Bumping a version

Move to a new release without ever changing what the old coordinate meant.

The whole procedure, in the order that lets consumers roll over one at a time:

shell
# 1. Add the new version alongside the old one. This does not retire anything.
dac add backend-app/geo-database@2026.09 \
  https://example.com/geo/2026.09/database.bin --pin

# 2. Move consumers over. Both versions resolve, so this can be a normal PR.
#    dac path backend-app/geo-database@2026.09

# 3. Retire the old one when nothing references it.
dac remove backend-app/geo-database@2026.08

# 4. Commit both project files together.
git add dac.json dac-lock.json

--pin records the digest the asset resolved to as its integrity value, so every later command holds the publisher to the bytes this add saw. Without it the lock file still pins the bytes; the manifest just does not say so.

The two failures you will meet, and what they mean

CodeWhat happenedWhat to do
version_rebind A coordinate the lock already binds resolved to different bytes — the origin replaced them behind a stable URL, or the manifest was edited to point that version somewhere else. Add a new version. If the source is genuinely rolling and you accept the change, dac pull --refresh-lock --rebind.
version_collision Two versions of one asset name the same bytes, or a new version resolved to bytes a retired version already had. Almost always: the URL was not changed along with the version. Point the new version at the source it was meant to have, or drop it. One of the two is a label, not a version.

Both errors carry the data in JSON details: lockedDigest and resolvedDigest for a rebind, the two versions and the shared digest for a collision. You never have to re-download anything by hand to find out what changed.

Editing the manifest by hand

Nothing resolves a hand edit until you ask:

shell
$EDITOR dac.json
dac pull --update-lock    # resolves only what the lock does not describe
dac verify                # confirm the two files agree before committing

dac add --offline is the same idea from the other direction: it updates only dac.json, makes no request, and leaves dac-lock.json alone for a later pull --update-lock. Useful when you are adding ten assets on a plane.

08

Make and build-script integration

Let a build system depend on an asset without teaching it anything about DAC.

Makefile
GEO := backend-app/geo-database@2026.08
TOOLCHAIN := tools/toolchain@1.4

.PHONY: assets
assets:
	dac pull --progress=false

# A recipe asks for the path at the moment it runs, so a stale cache object or
# a missing pull fails here with a real message instead of a confusing one.
vendor/toolchain/bin/tool: assets
	mkdir -p vendor/toolchain
	tar -xzf "$$(dac path $(TOOLCHAIN))" -C vendor/toolchain

build: assets vendor/toolchain/bin/tool
	./build.sh --geo-database "$$(dac path $(GEO))"
Do not call dac path at parse time

GEO_DB := $(shell dac path ...) runs before assets has pulled anything, so a cold checkout fails with an empty variable rather than a message. Call it inside a recipe, where a failure stops the build with cache_object_invalid: The cache object is missing. Run dac pull.

The same pattern in a plain script, with the paths resolved once up front:

build.sh
#!/usr/bin/env bash
set -euo pipefail

dac pull --progress=false

geo_database="$(dac path backend-app/geo-database@2026.08)"
policy_bundle="$(dac path platform/opa-bundle@1.12.0)"

# The paths are inside the shared cache and the objects are read-only, so treat
# them as inputs: copy or extract, never write in place.
install -D "$geo_database" build/data/geo.bin
tar -xzf "$policy_bundle" -C build/policy

Cache objects are installed read-only. A build step that wants to modify an asset must copy it out first — which is the same discipline that makes the cache shareable between projects.

09

Runner cache hygiene

Keep a long-lived shared cache bounded and honest.

scripts/dac-hygiene.sh — run weekly
#!/usr/bin/env bash
set -euo pipefail

export DAC_CACHE_DIR=/var/cache/dac

# See what would go before it goes.
dac cache gc --max-age 14d --dry-run

# Collect objects nothing has used in two weeks, plus temporary files left by
# interrupted downloads and sidecars whose object is gone.
dac cache gc --max-age 14d

# Hash every object in the shared cache and drop the ones that no longer match.
# Without --repair this exits 1 when it finds damage, which is the scripted
# signal to act; with --repair it removes them and a later pull replaces them.
dac cache verify --all --repair
  • Age is the only liveness signal a content-addressed store has. Every cache hit refreshes the object's sidecar timestamp, so --max-age means "nothing has used this in that long", not "this was downloaded that long ago".
  • Collection never removes a digest lock file. Unlinking a lock another process holds would let a later process take the same lock through a new inode.
  • cache gc collects the whole shared cache and reads no project files. Run it on the machine, not per project.
  • Ordinary commands already detect damage by comparing an object against the sidecar written at install. cache verify answers the harder question — storage that changed bytes without changing the stat — at the cost of reading everything it checks.

Recovering a damaged cache is two commands, and no project file changes:

shell
dac cache verify --repair   # remove the corrupt objects this project locked
dac pull                    # download them again and install good bytes

Damage is reported wherever it turns up: dac path and dac export refuse, dac info reports cache: corrupt, and dac pull downloads the asset again and reports it as repaired.

Automation

Scripting DAC

Use --json (or -j) to write one versioned JSON document to standard output. Human errors, help, and progress go to standard error; JSON mode writes no human summaries, and pull also disables progress in JSON mode so that exactly one document lands on stdout.

success envelope
{"outputVersion":3,"ok":true,"command":"path","data":{}}
error envelope
{"outputVersion":3,"ok":false,"command":"pull","error":{
  "code":"network_error",
  "message":"The asset request failed.",
  "cause":"https://example.com/db: unconditional request returned HTTP 404",
  "details":{"asset":"backend-app/geo@1.0.0","status":404,"url":"https://example.com/db"}}}

code and message are stable enough to branch on, which is exactly why neither says anything specific about a failure. cause carries the part an operator acts on, and details repeats the useful parts of it as data.

A defensive wrapper

shell
#!/usr/bin/env bash
set -euo pipefail

if ! out=$(dac pull --json 2>/dev/null); then
  code=$(printf '%s' "$out" | jq -r '.error.code // "unknown"')
  case "$code" in
    lock_stale|lock_missing)
      echo "The lock file is out of date. Commit a pull --update-lock." >&2 ;;
    cache_object_corrupt)
      dac cache verify --repair && dac pull ;;
    *)
      printf '%s' "$out" | jq -r '.error.cause // .error.message' >&2
      exit 1 ;;
  esac
fi

printf '%s' "$out" | jq -r '.assets[] | "\(.coordinate)\t\(.status)\t\(.path)"'

Every asset a command touched comes back with its whole coordinate plus namespace, name, and version separately — the whole is what you pass back to dac path, the parts are what you branch on. Statuses you will see from pull: cached, downloaded, not_modified, distdir, repaired.

Scope

Non-goals

Knowing what a tool refuses to do is how you decide whether to adopt it. DAC's list is short and it is not going to grow.

It does not unpack, install, or run anything

Extraction and installation belong to whatever consumes the path dac path returns.

It does not order or compare versions

No ranges, no constraints, no latest, no dependencies between assets. It has no idea whether 10 follows 9, or whether either is a number.

It hosts nothing

No mirror, no remote cache, no registry, no plugin language.

It records no signature or provenance

A digest says the bytes did not change. It does not say who made them.

It resumes no partial download

A failed transfer starts over. Objects are installed only after the whole stream has been hashed and checked.

It does not track upstream releases

verify --refresh reports that an origin changed what it serves at a URL you already have. Nothing tells you a newer version exists.

There is also no Windows build. The cache coordinates concurrent processes with flock, and the Unix build constraint makes that explicit rather than letting it fail somewhere deep in the cache.
